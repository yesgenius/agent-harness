# Наряд агенту

Наряд описывает результат словами поведения. Агент сам решает, как сделать; вы решаете, что считается сделанным. Заполните и положите в `docs/work-orders/`: запуск под целью ссылается на этот файл. Правила папки — в `docs/work-orders/README.md`. Наряд без цели можно вставить прямо в разговор, но тогда в git он не останется.

```markdown
# Наряд: <что должно стать возможным>

## Зачем
<Кто и что сможет сделать после этой работы. Одно-два предложения.>

## Что должно быть видно
1. Открываю <что>, делаю <что> — вижу <что>.
2. Когда <особый случай>, вижу <что>, а не <что>.

## Чего не должно случиться
- <То, что сейчас работает и не должно сломаться.>

## Спецификации
- Привести `docs/specs/` в соответствие с новым поведением в этой же работе: <какие разделы затронуты, если известно>.

## Границы
- Не трогать: <что>.
- Спросить меня, прежде чем: <что>.

## Отчёт
Файл: docs/temp/<наряд>.md, с тем же именем, что у наряда. Раздел «Что проверено»: каждый пункт из «Что должно быть видно»,
как проверено, что наблюдалось. Раздел «Изменённые сторожа»: вывод команды
`git status --short --untracked-files=all -- tests/guards example/tests/guards scripts .githooks package.json harness.config.json .claude/settings.json .codex .mcp.json docs/specs/GUARDS.md`
(сторожа, намеренные поломки, проверки сборки, хуки, запреты агентов и всё, откуда сторожа читают правила)
и для каждого файла из него: какое правило теперь проверяется иначе и почему. Вывод пуст — в разделе одно слово «нет».
В конце ручная проверка: что открыть, что сделать, как выглядит правильно, какой фильтр логов снять, если не так.
```

Запуск под целью, одинаковый для обоих агентов. Строку вставляет владелец: агент сам себе цель не ставит.

```text
/goal Выполни наряд docs/work-orders/<наряд>.md. Условие выполнения: агент вывел в этот разговор разделы «Что проверено» и «Изменённые сторожа» отчёта docs/temp/<наряд>.md: в первом каждый критерий наряда назван, а рядом указано, чем он подтверждён, во втором перечислены изменённые сторожа или написано «нет»; и последние запуски npm run build и npm test в этом разговоре завершились успешно; либо агент вывел в разговор вопрос к продукту, без ответа на который работа не может продолжиться, и остановился; либо прошло 200 ходов. Последним сообщением агент называет выход: «выполнено», «нужен ответ» или «не закончено: прошло 200 ходов»; при двух последних перечисляет, что не сделано и что нужно, чтобы продолжить.
```

Что здесь важно:

- Наряд запускается на чистом дереве: всё прежнее закоммичено. Тогда после работы `git status --short docs/specs/` называет каждый изменённый и новый файл спецификаций этого наряда, а `git diff docs/specs/` показывает правки в уже существовавших; новый файл он не показывает, его откройте целиком. Прочитайте эти изменения до ручной проверки: по нему видно, что работа поменяла в описании продукта. Если там что-то не так или непонятно, верните вопросы агенту.

- Раздел «Изменённые сторожа» закрывает дыру, которую сторожа не видят: агент может ослабить самого сторожа, и сборка останется зелёной. Заметить это может только человек. Если в разделе не «нет», прочитайте объяснение до ручной проверки: правило, которое поменялось без вашего решения, — повод вернуть работу.

- Подтверждение печатается в разговор. В Claude Code выполнение условия судит отдельная модель, а она видит только разговор и файлов не читает. В Codex условие проверяет сам агент.
- У условия три выхода. Без вопроса к продукту агент будет домысливать, вместо того чтобы спросить; без предела ходов он может не остановиться. Выполнена цель только при первом выходе: два других останавливают работу, но не завершают её, поэтому агент называет выход и перечисляет, что не сделано.
- Текст цели не длиннее 4000 символов, поэтому подробности лежат в наряде, а не в строке запуска.
- Критерии написаны так, что проверить их можно не читая код.
