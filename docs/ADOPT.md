# Как перенести обвязку в свой проект

Инструкция для человека, который не пишет код. Команды выполняет агент, вы описываете результат и принимаете его.

Нужны Node, git, GitHub и один из агентов: Claude Code или Codex. Если подписки нет, начните с неё: без агента обвязка бесполезна.

Сама обвязка написана на JavaScript, а проект может быть на любом языке. Проверки синтаксиса и консоли умеют только JavaScript: если у вас другой язык, на шаге 2 добавьте к промпту «перепиши проверки синтаксиса и логов под язык проекта и покажи, что они падают на нарушении».

**Предупреждение.** Настройки шаблона разрешают агенту выполнять команды без подтверждения. Держите проект в отдельной среде без личных данных и секретов. `docs/specs/AGENT-FRONT-ENDS.md` объясняет, как включить подтверждения.

## Шаг 1. Посмотрите, как это ломается

Попросите агента:

```text
Склонируй https://github.com/yesgenius/agent-harness во временную папку, выполни npm install и npm run demo:guards. Покажи мне вывод целиком и объясни каждую строку словами поведения.
```

Демонстрация ломает копию репозитория восемнадцатью способами и показывает, какой сторож остановил каждый. Это главное, что стоит увидеть: обвязка не текст с пожеланиями, а проверки, которые падают.

## Шаг 2. Перенесите ядро

Откройте агента в своём проекте и вставьте:

```text
Перенеси в этот проект обвязку из https://github.com/yesgenius/agent-harness:
AGENTS.md, harness.config.json, .githooks/, .claude/, .agents/, .codex/, .mcp.json, .nvmrc,
.gitattributes, scripts/, tests/guards/, docs/specs/, docs/ADOPT.md, docs/SKELETON.md,
docs/WORK-ORDER-TEMPLATE.md. Объедини .gitignore и скрипты package.json, ничего моего не удаляя.
Папку example/ перенеси тоже: она убирается отдельным шагом. Затем npm install, npm run build,
npm test. Покажи результат. Если у проекта уже есть инструкция для агента, не стирай её:
покажи мне, что в ней есть, и предложи, куда это перенести в AGENTS.md.
```

Результат: сборка и тесты зелёные на вашем проекте.

## Шаг 3. Расскажите агенту о продукте

```text
Заполни раздел Project-Specific в AGENTS.md. Задавай мне вопросы по одному, словами поведения:
что делает продукт, для кого, что в нём необратимо (деньги, письма, удаление, публикация),
какие внешние сервисы он использует, что запрещено менять без меня. Код читай сам, меня о нём не спрашивай.
```

Ответы на эти вопросы и есть ваша главная работа. Агент не знает, что для вас дорого.

## Шаг 4. Заполните контракт выпуска

```text
Заполни docs/specs/RELEASE.md для этого проекта. Спроси меня, где продукт публикуется, кто нажимает последнюю кнопку и что делаем, если выпуск сломан. Последний шаг всегда остаётся за мной.
```

## Шаг 5. Назовите самый дорогой провал

Вспомните, что было бы хуже всего: двойное списание, письмо не тому, потерянные данные. Затем:

```text
Самое дорогое, что может сломаться: <опишите>. Опиши этот процесс моделью как example/process/reminder.fsm.json: состояния, переходы, какой шаг необратим и что записывается до него. Логи переходов с префиксами id. Покажи модель таблицей, я проверю её как процесс.
```

Таблицу вы читать можете: это описание процесса, а не код. Если там нет случая, который вы знаете, скажите об этом.

## Шаг 6. Уберите пример

```text
Удали example/ и docs/specs/PROCESS-REMINDER.md. Обнови harness.config.json: processModels и logging укажи на код проекта, regression поставь в null, пока своих образцов нет. Убери сценарии примера из docs/specs/REGRESSION.md. В docs/specs/GUARDS.md замени ссылки на example/ ссылками на своих сторожей или убери эти строки таблицы. Запусти npm run build и npm test: сторож ссылок покажет всё, что ты пропустил.
```

## Шаг 7. Первый наряд

Возьмите настоящую задачу и заполните `docs/WORK-ORDER-TEMPLATE.md`. Опишите, что будет видно, а не как делать. Запустите под `/goal`. Вы проверяете только результат по списку в конце отчёта.

## Шаг 8. Превращайте поломки в сторожей

Это единственный шаг, который не заканчивается. Каждый раз, когда что-то сломалось, а проверки молчали:

```text
Вот что случилось: <опишите>. Почему этого не поймали? Добавь сторожа по docs/specs/GUARDS.md, посади нарушение в scripts/lib/plants.js и покажи, что сторож падает на нём.
```

Обвязка не появляется в готовом виде. Она растёт из ваших поломок, а шаблон только экономит те, что уже случились у других.

## Что взять сразу, а что потом

| Когда | Что | Зачем |
| --- | --- | --- |
| Первый день | Инструкция, сборка как вход, воркфлоу `commit` и `rollback` | Агент работает по правилам, а любая ошибка откатывается |
| Первая неделя | Спецификации с индексом, барьеры веток, первые сторожа | Агент перестаёт додумывать, ветка выпуска защищена |
| Первый месяц | Модель опасного процесса, логи переходов, браузерная полоса | Сломанный прогон можно прочитать, агент видит продукт |
| Перед выпуском | Прогон по образцам, контракт выпуска, независимое ревью | Вы принимаете поведение, не читая дифф |

Работаете с одним агентом? Второй полезен для ревью: дифф проверяет тот, кто его не писал. Если всё же решили убрать:

```text
Убери из обвязки всё, что относится ко второму агенту: его настройки, парные воркфлоу, посаженные нарушения и проверки пар. Проверки первого агента оставь. Покажи, что npm run build и npm test зелёные.
```

## Как понять, что обвязка работает

- Вопросы агента понятны без чтения кода.
- Отчёт заканчивается ручной проверкой, которую вы можете выполнить.
- Сломанное находит сборка или сторож раньше вас.
- Вы можете уйти на час, и агент остановится на вопросе, а не на догадке.

Если агент спрашивает о коде или заканчивает словом «готово» без проверки, обвязка ещё не держит. Запишите это как правило, затем как сторожа.
